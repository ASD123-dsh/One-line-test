## 用户侧流程

当前源码将以下两项并入右上角“配置 / 诊断”菜单，与配置管理、诊断导出和恢复
指引分组展示，不再显示独立 `?` 按钮。该菜单调整已包含在用户验收的 V1.58.3 EXE，
功能和分发说明见 [V1.58.3 发布说明](releases/v1.58.3.md)，构建证据见
[菜单合并与打包记录](menu-unification-20261019.md)。

- **检测更新**：用户主动检测 GitHub 最新稳定版。发现更高版本后自动下载完整
  ZIP，显示进度并验证下载大小、GitHub SHA-256 摘要、包内清单和逐文件摘要。
  校验通过后，用户点击“升级并重启”并确认，才进入安装。
- **扫码反馈**：继续打开原有作者联系二维码和授权有效期页面。

软件启动时不会自动检测，不需要用户提供 GitHub 账号或令牌。检测和下载在后台
执行，不阻塞界面。关闭下载窗口会先取消任务并等待后台结束；网络失败或下载损坏
不影响现有程序。

升级确认框会提示先导出需要保存的包组。更新器校验文件归属并准备好同盘候选和
最小备份后，原程序才停止发送、关闭串口并退出。独立更新器逐个替换本工具文件，
重新启动并等待界面确认，再清理本次备份。安装目录本身不被搬动。

## 版本和附件约定

- 软件版本统一修改 `app_info.py` 中的 `APP_VERSION`，采用 `主版本.次版本.修订`
  三段数字，例如 `1.57.0`、`1.58.0`。
- `PROTOCOL_VERSION` 是原有协议说明版本，新增软件功能无需改变协议编码。
- 发布仓库固定为 `ASD123-dsh/One-line-test`，客户端只读取稳定 Release。
- 发行标签使用 `v` 加软件版本，源码与两个附件必须使用同一递增版本。
- 新主包：`AD-OneLine-v<版本>-windows-x64-managed.zip`，包含主 EXE、
  `_ad_oneline_internal/` 内全部依赖和独立更新器，以及 `ad-oneline-update-manifest.json`。
- 旧客户端过渡包：`AD-OneLine-v<版本>-windows-x64.zip`，保留旧 `_internal/` 和
  `update-manifest.json` 约定。它用于原独立目录旧版自动升级，不用于混放安装。
- 新客户端优先选择 managed 主包；旧客户端继续选择原附件名。两者都需发布相应
  `.zip.sha256`。客户端不接受单 EXE、RAR 或 GitHub 自动生成的源码 ZIP。

## 作者发布步骤

1. 与用户确定新版本号后更新 `app_info.py` 的 `APP_VERSION`，保持版本递增。
2. 在项目根目录运行回归测试：

   ```powershell
   python -B tools/check_project.py
   ```

3. 收到明确打包要求后，在有 PyInstaller 的 Windows 开发环境中运行：

   ```powershell
   python tools/build_release.py
   ```

   开发环境统一使用 Python 3.11.9 x64。收到打包要求后，按已验证基线安装工具：
   `python -m pip install -r requirements-build.txt`，不要临时升级 PyInstaller。
   终端用户不需要安装 Python 或这些开发工具。

   发布工具构建一个独立更新器和两个目录布局的主程序，在新的
   `dist/releases/v<版本>/` 候选目录输出一份主包程序文件夹、两个 ZIP 和两个
   `.zip.sha256` 校验文件。过渡布局只在临时构建目录中打 ZIP，不留下第二份
   可运行程序。新主包使用 PyInstaller 的专属 contents 目录。
   它不会自动上传 GitHub，也不会覆盖原来的 `dist` 正式程序或已有发布目录。
   如需重复构建同一版本，使用 `--output` 指定另一个新的目录。

4. 从新目录启动程序，使用隔离副本验证混放升级及失败回滚。用户明确确认功能通过后，
   提交、审阅合并并推送对应源码。在 GitHub
   Releases 创建同版本的稳定 Release，选择对应代码提交并填写更新说明。
5. 上传两个完整 ZIP 和两个校验文件，将该 Release 标记为最新版本。
   GitHub 会计算附件摘要，客户端使用 API 返回的 SHA-256 校验下载内容。
6. 核验公开最新版本、版本标签、实际下载及摘要后，保存真实发布记录，立即运行
   下文的本地归档收尾命令。归档完成并清理本次残留后，才报告发布完成；不要把
   最新正式包长期留在“升级测试”目录而漏掉正式发行版归档。

发布包必须由本工具构建；只把主 EXE 上传到 Releases 不足以提供自动升级。
现有较早的 `v1.0.0` 单 EXE 发行版不会导致客户端降级。

## 首次启用的迁移

之前已分发的 V1.56 没有检测更新功能，需要用户先手动下载并使用一次包含更新器的
完整新版本。以后再发布更高版本，用户即可通过“检测更新”完成下载和升级；
当前源码入口为 `配置 / 诊断 → 检测更新`，早期版本仍在 `?` 菜单中。

新的 managed 主包支持在任意名称的普通可写目录中与其他应用并存，不再要求目录名
固定。主 EXE、完整 `_ad_oneline_internal/` 和专属清单必须一起保留，不能只复制 EXE。
其他应用可以继续使用原 `_internal/`；不要让它们依赖本工具专属运行库目录。

旧版更新器不会因下载新包而提前升级自身。V1.58.1 及更早版本仍按整目录安装，并且
要求原程序文件夹名称；原独立目录可先通过过渡包升级。已经混放的旧版客户需手动
完整解压 managed 主包一次，或在受控测试副本中更新安装器和清单后再验证迁移。
旧版若缺少有效本工具清单，不能猜测哪些文件属于本工具，应手动使用完整主包。

源码运行可以检测和下载，但不会覆盖 Python 解释器或源码目录。

## 备份、数据和失败恢复

- 激活文件仍位于原有 `%APPDATA%/AD仪表一线通协议测试工具/`，更新器不访问或删除
  此路径。授权逻辑和有效期规则没有变化。
- 同级其他应用、未知文件、用户导出文件均保留原位，不参与读取、复制、备份、替换
  或回滚。内存中的未导出包组仍需在升级前自行保存。
- 按清单管理主 EXE、专属运行库文件及本工具清单。内容不变的受管理文件不改写，
  原本受管理但新版不再需要的专属文件才会移除。新路径撞上未知文件，或旧文件
  摘要与本工具清单不符时，停止升级并提示冲突，不覆盖其他文件。
- 从旧布局迁移时，共享 `_internal/` 不修改、不删除、不备份；新主程序改用专属
  运行库。旧共享目录可能还被其他应用使用，不能以“清理旧文件”为由删除。
- 本次事务位于安装目录内的 `.ad-oneline-update-随机标识/`，包含 `candidate/`、
  `backup/` 和 `transaction.json`。备份只保存本次会改动且原先存在的本工具文件，
  不包含用户文档、其他 EXE 或共享运行库。只备份改动文件，不是可独立运行的旧程序包。
- 新版界面完成本次启动确认并持续运行 5 秒后，提交事务并清理本次自有备份和
  候选文件。历史 `.backup-*` 或其他任务目录不批量扫描删除。
- 启动确认绑定随机标识、目标版本、主 EXE 路径和实际新进程号。仅创建进程成功
  不算升级成功；等待界面确认最长 60 秒，收到确认后有完整 5 秒观察窗口。
- 安装在目标同一磁盘准备候选目录，支持下载暂存在 C 盘而程序位于 D 盘的情况。
- 文件替换失败、无法创建新版进程、未收到界面确认或确认期间退出时会尝试恢复旧版。
  回滚前仅停止本次更新器启动的未就绪进程；无法停止或恢复受阻时保留备份并提示路径。
  自动清理成功后不再保留长期手动降级副本；这不是对所有协议功能的自动测试，
  新版运行一段时间后才暴露的问题需要重新下载旧版完整发行包处理。
- 每次文件改动前写事务记录，回滚只处理本次已尝试修改的文件。恢复材料被篡改或
  目标被第三方更改时停止覆盖、保留恢复副本，避免用回滚误删其他内容。
- 清理检查精确路径、随机标识、软件身份和文件摘要，按记录删除文件、只删除空目录，
  不递归删除未知文件。临时占用最多重试 8 次，间隔 250ms；清理受阻只记录警告，
  不把已确认成功的升级误报为失败。用户临时放进事务目录的未知文件也不会被删除。
- `.ad-oneline-update.lock` 阻止同目录并行升级。正常成功或回滚后释放本次锁；
  回滚未完成时保留锁和恢复材料，防止下次升级继续覆盖。强制结束更新器或断电的
  中断恢复需要按事务记录人工检查，本实现不声称具有断电后自动恢复能力。
- 更新器状态保存在系统临时目录的 `sifexe-update-*` 文件夹内。成功后清理大体积
  下载和解压副本，更新器自身和状态记录可在所有更新进程退出后再手动清理。
  `handoff.json` 中的 `backup_removed` 和 `cleanup_warning` 记录本次备份清理结果。
- 无写权限、本工具文件被占用、下载校验不通过等情况会停止升级并提示原因。
- 同一程序目录如果打开了多个工具窗口，请先关闭其他窗口后再升级。
- Windows 文件替换遇到访问拒绝或共享占用时，最多尝试 80 次，间隔 250ms；
  其他错误立即停止，不强制结束其他应用进程。文件恢复也使用相同的有限重试。
- 失败后的 `handoff.json` 保留失败阶段、原始 Windows 错误码、系统原因和完整异常链，
  便于区分临时文件占用、路径冲突和权限问题，不再只显示概括的失败提示。
- 安装动作始终由当前版本更新器执行。旧版首次升级仍可能保留一次整目录备份，
  本次功能从新版更新器执行安装开始生效；不能用旧安装器的结果代替新事务验证。

## 发布成功后的自动归档

开发侧每次正式发布成功后，默认执行 `tools/archive_release.py`，不需要用户再次
要求归档。它不联网、不发布、不编译，不在客户软件中增加后台任务。调用方必须先
完成 GitHub 发布及线上核验，并保存与 V1.58.2 相同结构的真实发布 JSON 记录。

首次收尾命令示例（后续替换为对应版本和实际输出路径）：

```powershell
python -B tools/archive_release.py `
  --source "dist/升级测试/release" `
  --record "dist/升级测试/reports/v1.58.2-publication.json" `
  --notes "docs/releases/v1.58.2.md" `
  --verification "dist/升级测试/packaging-verification.json" `
  --prune-source
```

该首次命令的源记录在成功收尾后会被清理。V1.58.2 已完成归档；需要重复核验时，
`--record` 改用 `dist/历史归档/正式发行版/v1.58.2/release-publication.json`，
`--verification` 改用同目录的 `packaging-verification.json`。

- 输出目录固定为 `dist/历史归档/正式发行版/v<版本>/`，包含两个 ZIP、两个校验
  文件、发布记录，以及提供的发布说明和打包验证记录。最新版本也必须在这里。
- 校验发布记录的仓库、已公开状态、标签和源码提交，以及四个附件的状态、大小、
  SHA-256；再校验 `.sha256` 文件的正文确实对应其 ZIP，避免归档错误版本。
- 归档只新增缺少的文件。已有文件内容相同则保留原位、不改写；不同则停止，
  不覆盖历史正式版。完整归档后再次逐个复核摘要。
- `--prune-source` 只删除归档已验证且内容未变的附件和生成记录副本。发布说明
  源码、未知文件和历史归档不删除。测试专属标记有效时，保留已打包入口固定读取
  的 managed ZIP 缓存；这是必要测试输入，不是另一个正式发行位置。
- 仍需按项目收尾规则清理本次自有构建目录、临时下载、已完成的测试副本和缓存；
  归档工具不对未知文件夹做递归删除，也不清理用户正在测试或未恢复完成的内容。

当前 V1.58.2 的补归档与验证记录见 [正式发行版归档记录](release-archive-20261015.md)。

V1.58.3 沿用用户已验收的菜单合并包，发布成功并完成实际线上核验后执行：

收尾后需要重复核验时，源目录、记录和验证文件改用
`dist/历史归档/正式发行版/v1.58.3/` 中的对应文件。临时 `build/` 记录在成功归档后
